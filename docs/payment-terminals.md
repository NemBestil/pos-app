# Payment-terminal monitoring

UDP on port 8000 supplies terminal IDs and addresses. For each configured terminal, a tablet reports it available when **either a local UDP broadcast or a successful TCP check occurred within the last five minutes**. Every broadcast renews availability, including repeated broadcasts from an unchanged endpoint. Cached discovery or server `lastSeenAt` values alone never establish current local access.

`PaymentTerminalReachability.java` owns the shared five-minute window, monotonic observation times, expiry timers, TCP scheduling and available endpoints. `ForwarderService.java` owns discovery, transport-independent calls and POS socket reporting. It retains both wall-clock and monotonic receipt times for local UDP observations so applying configuration can recognize an earlier broadcast without extending its original expiry.

App 1.4.8 opens and closes the discovered/configured TCP port (**443 for v1**, **8080 for v2**) once per minute with a **10-second connect timeout**. TCP success is sufficient for availability; signed DeviceInformation verification is not a prerequisite for monitoring. TCP checks use ordinary sockets and forwarded HTTP calls use `URL.openConnection()`, letting Android route traffic over its default connection (including Ethernet or a routed mobile/VPN connection). They never require a Wi-Fi callback or bind to a Wi-Fi network. The terminal address must still be reachable through that connection. The newer of local discovery and server address observations supplies the target.

A failed TCP check allows three retries after the first attempt, with at least 10 seconds from completion of one attempt to the next. Failures, including exhausted retries, never override recent UDP/TCP evidence. Availability expires five minutes after the most recent successful observation, with an immediate device report, even during a pending check. Offline monitoring continues every minute and either a broadcast or TCP success can restore access. Default-network/endpoint changes clear old availability; in-flight results from replaced states are discarded. A fresh broadcast for the new endpoint immediately establishes its availability.

Monotonic per-terminal deadlines launch independent workers; printer availability never gates terminal checks. A separate timer sends `devices.snapshot` every minute, including an empty available list. Observations and expiry report immediately without waiting for printer scans. `lastSeenAt` is the wall-clock time of the most recent local UDP/TCP observation; wall-clock changes do not extend the five-minute window.

Registration/snapshots report `terminalCandidates` separately from available `devices`. Only GET `/api/v1/DeviceInformation` over pinned TLS or signed GET `/api/v2/DeviceInformation` setup requests may use unavailable candidates, preserving automatic authorization and manual credential edits. Payments and other operations require available endpoints. UDP/TCP reachability is not payment authorization: credentials, signed responses and the POS checkout status/busy check remain enforced by the server. The Capacitor discovery plugin exposes UDP observations only. The UDP listener binds wildcard port 8000 without selecting a transport, so broadcasts can arrive over Ethernet or Wi-Fi. The Wi-Fi multicast lock only helps broadcast delivery on Wi-Fi and is not a connectivity requirement. A default-network callback resets stale discovery/reachability after routing changes; it never gates requests or TCP checks.

Configuration no longer includes `canVerifyIdentity`, and monitoring has no credential-capability gate: every configured terminal is checked. The POS retains the identity-probe socket topics, address observation `lastSeenAt`, and legacy signed configuration probe. Current monitoring does not request identity probes. Android socket protocols 3/4 and forwarded operation payloads are unchanged. This fix requires a newly built and installed APK; a web-only update cannot replace native monitoring. No new POS API or migration is required for this fix.

Physical validation should cover UDP-only access despite failed TCP, TCP-only access without UDP, repeated unchanged broadcasts, exhausted retries within the five-minute window, exact expiry and recovery, configuration reapplication without refreshing stale evidence, clock changes, Ethernet-only operation with Wi-Fi disabled, default-network/IP changes during I/O, configuration without `canVerifyIdentity`, and adding/authorizing a terminal. Compile Java through the existing source-linking script with JDK 21.

## Direct local checkout in app 1.4.9

`DirectCardPaymentPlugin` exposes `getStatus`, `start` and `cancel` only to the origin currently configured in ForwarderService. Status reports the stable forwarder ID, currently reachable terminal IDs and terminal IDs with unacknowledged direct payments. The hosted POS must independently require a detected Android app version >=1.4.9. Unknown versions, older APKs and browsers keep their existing forwarding flow.

The hosted POS prepares a mutable RegisterCardCheckout and short-lived pre-signed DeviceInformation, payment and abort envelopes whenever its total changes. A tap calls the bridge before the fiscal HTTP request. The native runner shares the ordinary per-terminal executor, requires current reachability and a live identity/busy check, and uses `SamportTerminalConnection` for both APIs. v1 omits optional cashier IDs, submits PaymentsAsync once and polls only that persisted operation ID; v2 returns the unmodified signed response. Ordered distinct request timestamps avoid replay rejection. Preflight failure cannot authorize an automatic payment resend.

Before scheduling any I/O, native preferences commit the origin/checkout identity. A repeated call with that identity never starts another payment. Raw outcomes are saved until accepted by POST `/api/_internal/direct-card-payment` with the existing private Android-sync token. Five bounded result-only retries, device snapshots and register status checks retry delivery. Recovery after a process death reports unknown rather than resending POST. Acknowledged records retain a minimal once-only tombstone until 24 hours beyond expiry. No native request or result headers enter diagnostics.

The server verifies exact capability/session/signature/terminal/amount/currency/attempt matching. Only after that acknowledgement does the bridge emit the safe `outcome` event so the POS can display terminal approval while fiscal posting finishes. `terminal.direct-cancel` identifies the originating checkout; native cancels its pending start or aborts only its submitted operation. A fiscal failure after approval is handled by the server's existing exact-reference reversal workflow. PrintJob dispatch remains gated on a successfully posted sale and uses the ordinary printer protocol.

The source version is 1.4.9 (versionCode 101050). POS source prepares target/inclusive maximum 1.4.9 with minimum 1.4.7. Publish and verify the signed public 1.4.9 APK before deploying that target to production. A matching-signature profile build is installed directly on the connected development iMin; no public APK publication or production POS deployment is performed. Validate generation, Capacitor sync/source linking and JDK 21 Java compilation. Isolated native-D1/protocol checks cannot establish physical device lifecycle, payment latency or printer behavior.

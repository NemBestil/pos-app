# Installation app versions

The launcher owns POS Android updates. Read `app/composables/useAppReleaseUpdate.ts` for permission and update orchestration, `app/utils/app-version.ts` for version comparison/legacy requirements, and `app/app.vue` for installation lookup and the launch gate. Native download and system installation live in `resources/android/ApkUpdaterPlugin.java`.

On every launcher startup, ask for Android package-install permission if missing, independently of whether an update is needed. Opening Android settings is not a grant: recheck `canRequestPackageInstalls()` after returning. Denying permission still permits a compatible app to open a POS; accepting an update requires the permission. Startup initialization settles before a launch is allowed.

Before opening a new or saved installation, fetch `/api/public/installation` freshly. Its top-level `minAppVersion` and `targetAppVersion` are numeric `major.minor.patch` strings. The supported range is inclusive. Below minimum or above target requires the exact target APK and Cancel returns to the launcher. Within the range but below target recommends the target; Postpone continues normally. At target, open directly. Missing both fields means exactly `1.3.9`; partial or invalid ranges must fail. Do not select a global latest release or allow a mandatory update failure/cancel to navigate to the POS.

Download from `NemBestil/pos-app-releases` only. Tags remain `apk-x.y.z` and `apk-x.y.z-pre`, with matching prerelease flags and a public `.apk` asset. Stable apps choose the exact stable target; test apps prefer that stable target and can choose its corresponding prerelease if needed. The old independent background/latest-release checker has been removed because it does not know the selected installation's range.

The hosted POS may navigate back to `https://localhost/?reason=app-version` after logging out an incompatible app. Capacitor serves the packaged launcher at that origin. Consume the reason and show the logout/update notice without automatically reopening an installation.

The first version with this protocol is `1.4.0`. Existing APKs retain their embedded update code until replaced; plan the initial device upgrade before deploying the hosted POS removal of update UI. Publish the target release before deploying its requirements and keep `apk-1.3.9` available for legacy installations. Android cannot install a lower `versionCode` over a higher one: a too-new app or this launcher opening a legacy installation requiring `1.3.9` can require manually reinstalling the appropriate signed APK or changing the installation's supported range. The native updater checks the downloaded package ID and reports lower version-code rejection; never uninstall or erase data automatically.

The release workflow in the source repository publishes to `NemBestil/pos-app-releases`, using its `main` branch for release tags. Set `APP_RELEASES_TOKEN` as an Actions secret in the source repository with Contents write access to the release repository. Keep existing Android signing secrets there and preserve the signing certificate and application ID. Use `npm run tag:apk -- full` or `npm run tag:apk -- pre` to create the annotated tag with release metadata; unsigned/lightweight manual tags do not satisfy CI.

CI SDK setup uses `android-actions/setup-android@v4` with the explicit packages `platform-tools`, `platforms;android-36`, and `build-tools;36.0.0`. The action installs command-line tools and accepts SDK licenses itself. Do not request the removed legacy `tools` package or duplicate license acceptance in a shell pipeline; v3's default package list can fail before the APK build starts.

Workflow fixes must be committed into the release tag's source commit. Re-running an existing GitHub Actions run uses its original commit/ref and does not pick up a newer workflow from the default branch.

Validation: generate the Nuxt shell, sync Capacitor, run `scripts/android-patch.sh`, and compile Android Java with JDK 21. On a physical Android device, verify first-start install permission, legacy/malformed ranges, minimum/target/too-new versions, optional Postpone, mandatory Cancel, installer cancellation, missing APK/network failure, and hosted-POS return-to-launcher messaging.

App `1.4.1` introduces receipt-delivery socket protocol `4`: document frames replace the old root raw payload and the APK owns native feed/CUT and its 500 ms pause. The APK accepts the framed contract; the hosted POS also accepts older protocol 3 APKs and selects raw payloads with CUT commands for those receivers. Publish `apk-1.4.1` before the hosted installation requires it. See [receipt printing](receipt-printing.md).

App `1.4.2` retains protocol `4`, adds queued printer-completion status for ESC/POS receipts over Bluetooth, LAN and USB, and extends native cutter recovery to 1,000 ms before the next document/copy/job or final success. Its ESC/POS printers must expose a readable return channel and respond to `GS r 1`; unsupported/missing replies fail before paper data is sent, and the app never advances an unconfirmed body. Publish `apk-1.4.2` before increasing an installation's target to that version; the minimum may remain at `1.3.9` for legacy text-printing devices.

App `1.4.3` retains protocol `4` and makes queued completion status advisory: there is no preflight gate, and absent/failed reads or missing USB bulk IN use timed recovery. Body/cutter status share 14 seconds after each body, followed by the 1-second pause; status alone never fails the job or prevents later pages/jobs. Publish `apk-1.4.3` before raising an installation's target.

# Installation app versions

Published app 1.4.7 already discovers POS 1.3 and Cloudflare 1.4 through `*.nbpos.eu`. The router selects registered POS 1.4 installations; the selected backend's exact app-version range remains authoritative. POS and Android app version numbers are independent: POS 1.4 source keeps minimum Android app 1.4.7 and prepares target/inclusive maximum 1.4.10; existing devices may postpone the update. Publish the signed 1.4.10 APK before production rollout. No new APK is needed for routing or native location reports: production POS 1.4 retains the POS 1.3/legacy-whoami signing key. See [backend compatibility](backend-compatibility.md) for the original APK's external whoami dependency and shared signing setup.

The launcher owns POS Android updates. Read `app/composables/useAppReleaseUpdate.ts` for permission and update orchestration, `app/utils/app-version.ts` for version comparison/legacy requirements, and `app/app.vue` for installation lookup and the launch gate. Native download and system installation live in `resources/android/ApkUpdaterPlugin.java`.

On every launcher startup, ask for Android package-install permission if missing, independently of whether an update is needed. Opening Android settings is not a grant: recheck `canRequestPackageInstalls()` after returning. Denying permission still permits a compatible app to open a POS; accepting an update requires the permission. Startup initialization settles before a launch is allowed.

The launcher checks the selected installation on startup, selection, return to the launcher/app and browser online events, with visible checking/connected/unavailable states and retry. These checks never open the update prompt or navigate. See [launcher behavior and saved-domain migration](launcher.md). Before opening a new or saved installation, fetch `/api/public/installation` freshly. Its top-level `minAppVersion` and `targetAppVersion` are numeric `major.minor.patch` strings. The supported range is inclusive. Below minimum or above target requires the exact target APK and Cancel returns to the launcher. Within the range but below target recommends the target; Postpone continues normally. At target, open directly. Missing both fields means exactly `1.3.9`; partial or invalid ranges must fail. Do not select a global latest release or allow a mandatory update failure/cancel to navigate to the POS.

Download from `NemBestil/pos-app-releases` only. Tags remain `apk-x.y.z` and `apk-x.y.z-pre`, with matching prerelease flags and a public `.apk` asset. Stable apps choose the exact stable target; test apps prefer that stable target and can choose its corresponding prerelease if needed. The old independent background/latest-release checker has been removed because it does not know the selected installation's range.

The hosted POS may navigate back to `https://localhost/?reason=app-version` after logging out an incompatible app. Capacitor serves the packaged launcher at that origin. Consume the reason and show the logout/update notice without automatically reopening an installation.

The first version with this protocol is `1.4.0`. Existing APKs retain their embedded update code until replaced; plan the initial device upgrade before deploying the hosted POS removal of update UI. Publish the target release before deploying its requirements and keep `apk-1.3.9` available for legacy installations. Android cannot install a lower `versionCode` over a higher one: a too-new app or this launcher opening a legacy installation requiring `1.3.9` can require manually reinstalling the appropriate signed APK or changing the installation's supported range. The native updater checks the downloaded package ID and reports lower version-code rejection; never uninstall or erase data automatically.

The release workflow in the source repository publishes to `NemBestil/pos-app-releases`, using its `main` branch for release tags. Set `APP_RELEASES_TOKEN` as an Actions secret in the source repository with Contents write access to the release repository. Keep existing Android signing secrets there and preserve the signing certificate and application ID. Use `npm run tag:apk -- full` or `npm run tag:apk -- pre` to create the annotated tag with release metadata; unsigned/lightweight manual tags do not satisfy CI.

CI SDK setup uses `android-actions/setup-android@v4` with the explicit packages `platform-tools`, `platforms;android-36`, and `build-tools;36.0.0`. The action installs command-line tools and accepts SDK licenses itself. Do not request the removed legacy `tools` package or duplicate license acceptance in a shell pipeline; v3's default package list can fail before the APK build starts.

Workflow fixes must be committed into the release tag's source commit. Re-running an existing GitHub Actions run uses its original commit/ref and does not pick up a newer workflow from the default branch.

Validation: generate the Nuxt shell, sync Capacitor, run `scripts/android-patch.sh`, and compile Android Java with JDK 21. On a physical Android device, verify first-start install permission, legacy/malformed ranges, minimum/target/too-new versions, optional Postpone, mandatory Cancel, installer cancellation, missing APK/network failure, and hosted-POS return-to-launcher messaging.

App `1.4.1` introduces receipt-delivery socket protocol `4`: document frames replace the old root raw payload and the APK owns native feed/CUT and its 500 ms pause. The APK accepts the framed contract; the hosted POS also accepts older protocol 3 APKs and selects raw payloads with CUT commands for those receivers. Publish `apk-1.4.1` before the hosted installation requires it. See [receipt printing](receipt-printing.md).

App `1.4.2` retains protocol `4`, adds queued printer-completion status for ESC/POS receipts over Bluetooth, LAN and USB, and extends native cutter recovery to 1,000 ms before the next document/copy/job or final success. Its ESC/POS printers must expose a readable return channel and respond to `GS r 1`; unsupported/missing replies fail before paper data is sent, and the app never advances an unconfirmed body. Publish `apk-1.4.2` before increasing an installation's target to that version; the minimum may remain at `1.3.9` for legacy text-printing devices.

App `1.4.3` retains protocol `4` and makes queued completion status advisory: there is no preflight gate, and absent/failed reads or missing USB bulk IN use timed recovery. Body/cutter status share 14 seconds after each body, followed by the 1-second pause; status alone never fails the job or prevents later pages/jobs. Publish `apk-1.4.3` before raising an installation's target.

App `1.4.4` checks configured payment terminals over TCP port 8080 every minute. It verifies signed DeviceInformation before the first check, after a failed check, and after network or address changes; three retries with at least 10 seconds between attempts precede an offline report. UDP remains discovery only for updated clients. Socket protocol `4` and the existing printing contract remain unchanged. Publish `apk-1.4.4` before raising an installation's target; keep the minimum at `1.3.9` so older APKs remain usable.

App `1.4.5` corrects native terminal availability to a five-minute window renewed by either a local UDP broadcast or TCP success. Monitoring no longer requires a signed identity probe, and retry exhaustion cannot clear recent evidence. This correction does not change installation version requirements or the socket contract. See [payment-terminal monitoring](payment-terminals.md).

App `1.4.7` is based on the `apk-1.4.5` source, removes Wi-Fi binding from terminal TCP/HTTP traffic and UDP discovery, and monitors all configured terminals without `canVerifyIdentity`. Its `versionCode` is `101048`, above the already-published `1.4.6` (`101047`), so that APK can update in place. Publish `apk-1.4.7` and confirm its APK asset before publishing the POS patch that requires exactly `1.4.7`. Socket protocol `4` and signed payment requests/responses remain unchanged.

App `1.4.8` (versionCode `101049`) adds Samport v1 pinned TLS, v0/v1 UDP discovery, actual terminal-port checks and manual IPv4 detection. Its hosted target is 1.4.8 and minimum remains 1.4.7; the server routes v1 jobs only through 1.4.8+. Publish the signed release before deploying the new target. See [terminal monitoring and verification](payment-terminals.md#samport-v1-and-app-148).

Release preparation for `1.4.8` on 2026-11-11 passed Nuxt generation, Capacitor sync, Android source/resource linking, release Java compilation and profile APK assembly with JDK 21. The public stable release must include `nembestil-pos3-app-1.4.8.apk`; verify its package version, versionCode and signing-certificate continuity with `1.4.7` after CI publishes it.

App **1.4.9** (versionCode **101050**) prepares the optional direct local checkout bridge, durable once-only submission, result outbox and checkout-targeted cancellation. The hosted fast path explicitly requires >=1.4.9 in addition to native capability/local reachability; browsers and older apps retain server forwarding. This source change does not publish an APK. POS source prepares target/inclusive maximum 1.4.9 while retaining minimum 1.4.7. Publish and verify the signed public 1.4.9 APK before deploying those requirements to production; the matching local profile build can be installed directly on the development iMin. See [direct local checkout](payment-terminals.md#direct-local-checkout-in-app-149).

App **1.4.10** (versionCode **101051**) adds optional Xprinter UDP discovery and MAC-confirmed automatic IP recovery. Older hosted POS versions keep ordinary scanning; newer POS versions fall back to ordinary scanning on older APKs. POS 1.4.48 prepares minimum app 1.4.7 and target/inclusive maximum 1.4.10. Publish the signed APK before deploying the new target. See [network printer setup and pending physical acceptance](network-printers.md). Automatic IP acquisition is verified by rediscovering the same MAC and opening its TCP print port; persistent DHCP after reboot remains unverified.

The 16 November 2026 reissue of 1.4.10 also includes the redesigned launcher, visible connection checks and retry guidance, resilient customer logos and migration of saved legacy installation domains to `nbpos.eu`. The owner confirmed that no customers had received the original release and explicitly authorized deleting and recreating its release/tag with the same version and versionCode. This is a pre-distribution replacement, not the normal procedure for updating an already distributed APK.

## Local APK rebuilds

The Android version does not identify the packaged launcher assets. Running Gradle alone packages the files from the last Capacitor sync, so an APK can report the current version while showing an older UI. For launcher changes, run `npm run generate`, `npx cap sync android`, and `./scripts/android-patch.sh` in that order before assembling the profile APK with JDK 21; the complete local build/install commands are in the root README. The patch script refreshes launcher icons and splash screens when their source changes; `npm run assets:generate` explicitly regenerates them.

Before replacing a local development installation, verify that the APK contains the current `.output/public` bundles under `assets/public/` and the expected navigation hosts in `assets/capacitor.config.json`. Compare its signing certificate with the installed APK, then use `adb -s <serial> install -r <apk>` to retain app data. Restart the app and verify the installed APK's contents as well as its version; a version match alone does not establish that the new UI was installed.

Release CI generates and syncs web assets from the tagged commit; these generated web directories are ignored by Git. The launcher redesign present locally on 16 November 2026 was still uncommitted and absent from `apk-1.4.10`. A build from that tag therefore contains the earlier launcher even with freshly generated assets. Commit the intended launcher sources and include them in a new release before expecting public APKs to contain that UI.
